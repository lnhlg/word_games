# 话本 · MVP Spec

## Problem Statement

我攒了一整套酒馆（SillyTavern）的资产：角色卡、世界书、预设，都是反复调过的。但我想要的不是"和一张卡聊天"，而是**让模型演出一部多角色的小说**——我自己不下场，只以导演的身份编排，可以随时退回过去重演另一条路。

现有的工具都卡在同一个地方：它们的中心是"对话气泡"，一屏只能容下一问一答。于是：

- 小说被切成一条条气泡，每次描写都被头像和边框打断，读起来不像在读故事；
- 每写一段我就得当编剧，因为没人告诉我"接下来可以往哪走"；
- 如果这一拍演砸了，我只能删掉重说，而删掉的那条路就永远消失了；
- 我改一个角色的设定，得回酒馆改卡、重新导出、重新导入，没有就地编辑的路径；
- 最要命的是，我不知道模型到底收到了什么。角色跑偏时我无法判断是卡写坏了、世界书没激活、还是排布把某段挤掉了。

## Solution

一个在本机跑的单页应用，把"素材管理 → 一局演出 → 回退重演"连成一条路：

**素材库**。角色卡、世界书、预设都叫素材，可以导入，也可以从零新建，任何一份都能随时编辑。导入不是单向的，只是"用解析器把表单预填好"。每次导入都产出一份保真度报告，明说哪些生效、哪些被读取但忽略、哪些被有损转换。

**一局**。选 2–5 张卡组成演员表，选一份世界书与一份预设，开演前可以先看"最终 prompt 预览"——花钱之前先确认装配没错。

**演出**。正文以小说排版呈现，不是气泡。每一拍收尾时浮出三条岔路，每条只写"如果让什么发生、会把局面引向什么方向"，不写结果。点一条就填进导演输入框，可以改；自己写指令也行。不满意就退回那个分叉点，换一条岔路重演——原来那条枝还在，能比较。

**状态**。右侧常驻面板显示场景、在场者与关系；默认只看表面上可见的信息，点开某个角色才看得到他的秘密与动机——作为导演我有权知道，但我也想保留"不想提前知道"的权利。

**可解释**。任何时候都能看到这一拍实际发出的完整 prompt、模型的原始输出、以及状态究竟有没有记上。这套东西的价值一半在"能演"，一半在"能查"。

## Implementation Decisions

### 形态

单进程本地 Node 服务，同时提供 HTTP API 与静态前端；数据落本地 SQLite；不引入账号、多租户、外部数据库或桌面壳（ADR 0002）。模型密钥存本地设置，界面明示风险。

### 素材

角色卡、世界书、预设统一为**素材**，靠 `kind` 区分、靠 `origin` 记录来源。每份素材保存三份内容：当前内容（可编辑）、导入原件（仅导入时存在，可还原）、保真度报告。导入与新建走同一个编辑器，导入只是"用解析器预填表单"。

保真度报告是结构化对象，至少包含四类信息：读取成功的字段、做了映射的字段、被忽略的字段、有损转换的字段，外加警告列表。报告在界面上必须可见——这是"导入"这个承诺的兑现方式。

### 对局的素材是冻结的

对局建立时，把演员表里每张卡的当前内容**复制**进对局，而不是引用素材。之后编辑素材不影响进行中的对局；要生效需显式执行"应用到本局"，并在此后新建消息才会用到新版本。

这不是保守，是重演的前提：退回第三拍换一条岔路重演，只有在素材相同时才是同一个故事。

### 消息树

消息以父指针组织，对局记录当前叶节点。从任意节点产生新内容 = 新建一条以它为父的消息并移动叶指针；旧枝不删。同一父节点下的多条叙事消息构成替选。导演指令也是消息，但属于另一类，它参与装配、可被回退，不产生岔路。

### 岔路

每条叙事消息携带若干岔路。一条岔路只有两段：**触发条件**（如果让什么发生）与**引向方向**（会把局面推向哪一类境地），不含具体结果、不含台词。选中哪条记录在消息的元数据里，回退到该分叉点时可见。

### 状态

状态是程序持有并校验的结构化事实：场景（地点、时间）、在场者、关系（以文字描述，不用数值）、关键备注。每拍结束存**全量快照**而非增量链——状态体量小，全量让回退与比较都变简单。

状态由模型按协议输出、程序校验；校验失败时该拍标记"状态未记录"，正文照常显示，且界面必须能看见这个降级。

### 装配

装配器是**预设解释器**，不是固定模板（ADR 0003）：按排布顺序遍历每一项，内置槽位展开为对应内容，自定义项原样注入，标记类项决定内容落点。排布走完后固定追加**导演模式补丁**，不可关闭——酒馆预设全部假设"单人 RP、对 {{user}} 说话"，不覆盖这层假设只会得到一段跑偏的单人对话。

多角色带来酒馆没有先例的语义：角色类槽位（角色描述、性格、场景）按演员表**逐个展开**，每个在场角色占一段；不在场角色不进入这些槽位，只在"在场名单"里保留一行摘要。

预算裁切发生在展开每个槽位的过程中，顺序为：示例对话 → 非在场角色摘要 → 记忆 → 最老的正文。世界书激活在装配之前按预算截好。

### 世界书激活

扫描最近四拍正文与本轮指令。常驻条目总是注入；主关键词任一命中即为候选；若条目启用次级关键词，则按预设逻辑做二次筛选；按位置决定注入到角色定义前、后或指定深度；预算不足时按顺序号从低到高截断。

不实现递归扫描、激活概率、分组评分与定时效果。它们被读取、被计入保真度报告、不生效。

### 输出协议

一次输出分三段：正文、状态、岔路，用固定标记界定。解析宽容是硬要求：任一段缺失或格式非法，只降级该段——状态丢失标记为"未记录"，岔路丢失则隐藏岔路区，**正文永不丢弃**。

正文出现裸宏同样属于静默错误，必须当作告警暴露，而不是让它混进读者的眼睛里。

### 宏与视角

实现核心替换宏与随机类宏，不做嵌套与作用域。导入时扫描素材中出现的宏，未实现的进保真度报告的警告列表。

导演不在场，因此 `{{user}}` 映射为可配置的视角名（默认"旅人"）；角色卡的 `first_mes` 语义改为**登场引子**——模型写这个角色首次登场时的参考片段，可为空，不再假设有人在被它搭话。

### 模型客户端

OpenAI 兼容协议，以流式为主。失败不推进消息树——重试必须能沿用完全相同的内容，否则重试的结果无法比较。

### 关键契约

```

Fidelity      { read[], mapped{}, ignored[], degraded[{field, reason}], warnings[] }

CastEntry     { material, roleLabel, secrets[], goals[], active }
```

### 界面

素材库页（列表、新建、编辑、导入、删除前引用检查）+ 对局页（演出版 / 状态面板 / 消息树三区）+ 装配预览 + 原始输出视图。演出版是小说排版；岔路区在正文之后浮现、视觉弱化、可关闭。

## Testing Decisions

**什么算好测试**：只断言外部可观察的行为。给定输入，断言输出——不碰内部字段名、不断言私有函数、不测实现顺序。测试的名字应该描述"导演能看到什么"，而不是"代码怎么跑"。

**两个接缝**（已与用户确认）：

- **导入接缝**：一个纯函数，输入字节与文件名，输出素材对象与保真度报告。零 IO、零网络，可以在毫秒级跑完几百个用例。
- **演出接缝**：一个单入口，输入素材快照、历史与本轮指令，输出装配后的 prompt、正文、状态、岔路与告警。依赖注入假的模型客户端——它返回固定文本并捕获收到的请求。于是"模型收到了什么"变成可直接断言的事实。

两个 seam 覆盖了本项目的全部静默失败面：卡解析成空描述、世界书条目没激活、槽位顺序错、状态没记上、岔路丢失、裸宏漏出。HTTP 路由与界面不在接缝内——它们的失败是显式的（500、白屏、报错），花在这上面只会得到脆的测试。

**fixtures**：需要真实文件，不接受手写的理想样本——PNG 卡（同时覆盖 `chara` 与 `ccv3` 两种标记）、JSON 卡（V2、V3、以及"V2 数据 + V3 标记"这种酒馆实际会产出的畸形组合）、独立世界书（`entries` 是对象 map）、卡内世界书（`entries` 是数组）、真实预设。

**必须覆盖的边界**：
- 空卡、缺 `spec` 字段、字段类型不对
- 截断的 PNG、含多个 tEXt chunk、`ccv3` 与 `chara` 并存时的优先级
- 世界书两套命名互转后的激活结果是否等价
- `prompt_order` 缺 `character_id`、引用不存在的项、全部项被禁用
- 模型输出缺状态段、缺岔路段、状态 JSON 非法、正文为空
- 预算不足时的裁切顺序是否与声明一致
- 多张卡时角色槽位是否为每人一段、不在场角色是否确实没进槽位

**运行器**：Node 内置测试运行器，零额外依赖。

## Out of Scope

- 世界书递归扫描、激活概率、分组评分、定时效果（读取但不生效）
- regex 扩展、STscript、Quick Replies
- 多用户、账号、租户隔离、远程部署
- 桌面壳（Tauri / Electron）
- 骰子与检定、战斗结算、数值成长
- 向量检索与 embedding 记忆
- 导出回酒馆格式
- 角色立绘、表情、语音
- 移动端适配
- 多人协作与共享对局

## Further Notes

**四条已知风险**

1. 一次输出要同时给出正文、状态与三条岔路，指令遵循负担重。小模型与廉价中转很可能只完成前一半——所以解析必须宽容，降级必须可见。
2. 单次调用演多个角色，容易写成同一个人在换名字。缓解手段是禁止轮流发言式流水账、完整人设卡、每角色独立的秘密与动机。
3. 上下文会早于预期地耗尽：多卡 + 世界书 + 长篇正文三者叠加。不在场角色只进摘要、滚动摘要、按槽位裁切都是为它准备的。
4. 枚举映射有损：卡内世界书与独立世界书是两套命名，注入位置的多值枚举会塌缩。必须在报告里说清，不能静默改写。

**阻塞项与前置**

- 需要一份真实的预设 JSON 才能校准排布解析（`prompt_order` 里的 `character_id` 语义尚未验证）。缺它就先按官方默认结构实现，并留好校准点。
- 需要至少一张真实角色卡作为 fixture，否则导入接缝测的是我编的理想样本。
